# 内容驱动的制作技术选择

每次用本 skill 创作视频时读取本文件。这里描述的是**决策和验收方式**，不是宣称当前 Canvas 脚手架已接入 Remotion、p5.js 或 Three.js。当前 `bin/new-video.mjs`、`bin/render.mjs` 只实现 Canvas 2D 路径。

## 先选画面方法，再选工具

对每一幕先写清：观众应理解的一个判断或关系、画面从什么状态变成什么状态、旁白的哪句话触发变化、人物与信息有什么关系。然后选最清楚、最省解释成本的画面方法。

| 要讲清的关系 | 优先画面方法 | 候选技术 |
|---|---|---|
| 定义、引言、少量要点 | 排版、插画、角色姿势与视线 | 现有 Canvas；复杂文字排版可用 Remotion + React/SVG |
| 两种观点或数据对比 | 对齐位置、共同标尺、同步变化 | Canvas 或 Remotion + React/SVG |
| 注意力筛选、群体行为、粒子流、自然生长 | 程序化二维运动，让相关元素逐步显现 | p5.js；需要简单效果时用 Canvas 即可 |
| 原因与结果、信息流、步骤搭建 | 随旁白逐步出现的连线、路径、结构 | Canvas、React/SVG 或 p5.js；有真实空间关系时才用 Three.js |
| 空间结构、尺度、视角切换、三维产品 | 摄像机与物体运动，叠加清晰的二维标签 | Three.js，经 `@remotion/three` 接入 Remotion |
| 多镜头、音频、字幕、转场的统一编排 | 共用一条帧时间轴和可预览的合成 | 复杂新项目优先评估 Remotion；简单项目可沿用现有导出器 |

不要让每套风格固定对应一种技术：漫画风也可以有 p5.js 的信息流；技术讲解也可能只需清楚的二维图。视觉惊喜来自**观众看见关系发生变化**，不是持续运动、满屏特效或强制 3D。角色动作要改变画面、回应对象或引导视线；旁白不是角色对白时，不让角色持续张嘴。

## 按幕记录决策

在项目 `STORYBOARD.md` 中逐幕记录：

- **核心意思**：观众看完这一幕能复述的单一观点。
- **画面方法**：比较、因果、筛选、逐步搭建、路径、空间解释、人物选择等；允许自定义。
- **起点 → 触发动作 → 结果**：关键动作对应最终配音的词/句时间，不在开头一次摆完。
- **主体和关系**：人物看向、触碰、使用或离开什么；对象如何响应。
- **技术与理由**：例如「p5.js：多条线索逐步汇成路径」或「Canvas：静态双人对比已足够」。不必对同类连续镜头重复长篇说明。
- **文字和风险**：短标签、字幕区域、不能暗示的额外结论。

可以复用的场景方法应抽象为内容协议，而非固定卡片模板。配置需独立保存画面风格、字幕、配乐、语言与音色；制作技术是项目/场景选择，不写死进风格包。新的场景家族先在真实样片中证明可读、可控，再进入公共框架。

## 推荐的组合方式

对需要多种画面和复杂编排的**新项目**，优先试用 Remotion 作为共同时间轴、预览和导出层：

1. 保留一份按最终配音对齐的场景、动作、字幕时间数据。所有画面从当前帧计算状态，暂停或跳到任意帧应得到同一画面。
2. 文字、漫画角色、二维标签和界面排版优先用 React/SVG/CSS 组件；角色与图解的互动由分镜事件驱动。
3. p5.js 只在二维程序化运动确实增加理解时使用。先用短段证明在逐帧导出中稳定；可做成由 Remotion 帧号驱动的独立画布，或先输出透明序列再合成。不要依赖自由运行的 `draw()`、累积 `frameCount` 或未固定的随机数。
4. Three.js 优先通过官方 `@remotion/three` 与 React Three Fiber 集成。3D 场景从 Remotion 帧号确定相机和物体状态；关键文字、字幕和指示标签仍用清晰的二维层。先验证目标机器的 WebGL/Chromium 导出能力。
5. 音频、字幕、转场和最终画幅由共同时间轴编排。同一数据生成分镜静帧、短段预览、最终 MP4；仅在用户需要网页探索时增加交互版。

当前 Canvas 导出器在 Chrome 中使用 `--disable-gpu`，不能把 Three.js 场景直接塞进现有 `window.__frame(t)` 管线并假定可用。Remotion 官方对 3D 的服务端渲染要求配置 Chromium `angle`。在迁移验证前保留现有 Canvas 路径；新路径通过后逐步把已验证的场景沉淀为可复用模块，而非一次性重写旧视频。

## 什么时候做交互版

视频内部的**人物与图解互动**是所有格式都应考虑的叙事设计。观众自己点击、拖动或切换参数则需要网页交付物；MP4 本身只按固定时间播放。用户明确需要探索、培训或产品演示时，可基于同一场景数据制作 Remotion Player / 网页版本，例如切换比较对象、拖动时间轴、显示解释层。不要因为用了 Remotion 就默认增加网页交付物。

## 新技术的进入门槛

先做 5–30 秒、能暴露主要风险的代表性样片，再扩展长片。检查：

1. 分镜的起点、关键词、结果与旁白一致；去掉字幕仍能大致理解，且没有新增原文未说的结论。
2. 同一时间点重复抽帧一致；跳帧、倒退预览、并行渲染后没有随机漂移或角色状态错乱。
3. 字幕逐句跟随最终声音，标签不遮挡主体，画面在目标分辨率和播放器尺寸下可读。
4. 实测预览、静帧和最终导出；记录帧率、分辨率、渲染时间、缺失依赖以及音画完整性。3D 特别检查 WebGL 可用性和导出环境。
5. 与现有方案对比：画面是否更容易看懂、是否明显提高完成度、增加的制作和维护成本是否值得。未通过时简化画面或回退到 Canvas，不为使用工具牺牲成片。

Remotion 短段样片还要特别检查**每幕第一帧**：不能让人物、主图和字幕全从完全透明同时开始，导致旁白已进入而画面只剩标题或背景。让主体在切幕时已有可识别状态，后续变化再跟关键词触发。以最终帧率把时长换算为整数帧，抽查切幕前后一帧与音频尾部；不要仅看每幕高潮帧。2026-09 的 13 秒双人漫画试片在本机以 Remotion 4、1920×1080、24 fps 完成了静帧与带音轨 MP4 导出；这证明了该组合的本机可行性，不代表其他机器或 3D 渲染已经通过验证。

长片还要做一次**全幕代表帧检查**，并在文字、角色和关系线同时出现的时刻单独抽帧。2026-09 的 84 秒双人漫画片中，实际发现过标签撞上人物、旧角色在转场中残留、说明文字压住节点等问题；逐幕静帧能发现静态碰撞，切幕前后与动作中点抽帧才能发现残留。修正后再从最终 MP4 抽帧、完整解码，并核对分辨率、帧率、音轨和时长。同一配音制作新旧版时，输出并排对比片，可直接判断新画面是否让观点更清楚。完整项目的已验证做法是 Remotion + React/SVG 编排 14 幕，复用批准的音轨和逐句双语字幕；本次没有需要 3D 或粒子模拟才能讲清的关系。

每次发现可复用的视觉表达、适配代码或质检方法，应更新到对应场景模块、风格资源或本 skill；文章特有的隐喻和素材留在该视频项目中。引入 Remotion 用于正式团队或自动化生产前，按实际用途核对其许可条件。
